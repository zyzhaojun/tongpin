# 同屏：Windows 局域网投屏开发方案

日期：2026-09-15

状态：0.2.1 预览版已实现。0.2.0 的自动发现、防火墙助手和双机画面链路已在两台真实电脑上验证；0.2.1 修复接收端全屏同步并等待双机复验。

## 1. 已确定的需求

- 专家使用笔记本，通过 Wi-Fi 将画面发送到 Windows 教学一体机，或连接电视的 Windows 电脑。
- 一次连接一台发送电脑和一台接收电脑。
- 首版采用免安装 Windows 程序，优先保证局域网独立使用。
- 同一个程序提供“我要投屏”和“接收投屏”两个入口。
- 使用时无需账号、订阅、授权服务器或互联网；所有界面资源随程序分发。
- 接收端可以通过网线接入同一个可互通的局域网。

建议首版平台为 Windows 10/11 x64，具体系统版本和硬件兼容性在技术验证阶段确认。Mac 发送端和电视原生系统接收端留待后续单独评估。

## 2. 使用流程

接收端：

1. 打开程序，选择“接收投屏”。
2. 首次运行时完成一次防火墙修复；等待并确认附近笔记本的连接请求。
3. 配对成功后全屏播放，可随时结束连接。

发送端：

1. 打开程序，选择“我要投屏”。
2. 从附近设备列表选择大屏；跨网段时直接输入 IP。
3. 选择屏幕或窗口。
4. 点击“开始投屏”，持续显示连接状态和“停止投屏”。

自动发现失败时始终保留地址输入。连接码用于配对，设备地址用于定位；在没有发现机制或目录服务时，单独输入短连接码不能定位电脑。

## 3. 推荐技术路线

采用 Electron + TypeScript + WebRTC，自行实现投屏界面和局域网连接流程，使用现有开源运行时的屏幕采集及音视频传输能力。

| 部件 | 首版实现方向 |
| --- | --- |
| 桌面窗口和绿色分发 | Electron；优先交付解压可运行的 Windows 包，再评估便携 EXE |
| 界面与状态管理 | TypeScript + HTML/CSS；保持界面简单 |
| 屏幕采集 | desktopCapturer + setDisplayMediaRequestHandler |
| 画面传输 | RTCPeerConnection；只建立视频轨道，音频请求会被拒绝 |
| 建立连接 | 接收端内置本地信令服务，负责配对及交换 SDP/ICE 信息 |
| 媒体播放 | 接收窗口绑定远端 MediaStream，提供全屏、静音和断开 |
| 自动发现 | 并行探测本机 IPv4 `/24` 网段中的 HTTPS 发现端点；IP 输入和完整连接信息作为回退 |
| 诊断 | WebRTC getStats + 本地应用日志 |

```mermaid
flowchart LR
    S[专家笔记本：选择屏幕或窗口] <-->|局域网配对与连接协商| R[Windows 接收端：内置信令服务]
    S -->|WebRTC 画面| P[接收窗口：全屏播放]
    R --- P
    P --> D[一体机屏幕或 HDMI 电视]
```

首版通过可互通局域网中的本地候选地址建立连接，不配置公网 STUN/TURN。若实际校园网禁止终端互访，应先解决网络可达性；公共中继不作为离线版本的隐藏依赖。

Electron 便于先验证端到端功能，但分发体积和内存占用较大。若实际设备表现不佳，再依据测量结果评估 Windows 原生采集和更轻的界面运行时。

## 4. 必须尽早验证的技术问题

### 屏幕和窗口

- 先支持整屏，再验证单独窗口、双显示器和不同缩放比例。
- PPT 放映可能使用独立窗口；需要验证从编辑态切换到放映态时的行为。
- 源窗口最小化、关闭或屏幕分辨率变化时，要停止或明确提示，不能一直显示旧画面并声称仍在直播。

### 媒体范围

- 0.1.1 只采集和传输视频轨道，不请求系统声音、麦克风或摄像头。
- SDP 校验和接收端轨道处理都会拒绝音频，避免误把声音带入会话。
- 声音同步列为后续需求，需另行评估采集权限、延迟和音画同步。

### 局域网连接

- 测试多网卡、VPN、不同网段、网线接收和 Wi-Fi 发送等组合。
- 区分“未发现设备”“地址不可达”“连接码错误”“媒体连接失败”。
- 首次接收时由防火墙助手创建 TCP 48765、`LocalSubnet` 范围的固定端口规则；学校组策略阻止本机规则时给出管理员指引，不要求关闭整个防火墙。

### 配对与停止

- 捕获必须由发送者明确选择并开始；结束后关闭所有媒体轨道和会话。
- 短连接码设有效期、失败次数限制和会话绑定；不把短码直接当作加密密钥。
- 信令需要加密并认证接收端身份。选用成熟的配对/密钥协商方案，或在首次连接时核验并固定接收端证书指纹；不全局忽略证书错误，不自行设计密码协议。
- 设备发现只公开名称和 TLS 身份，不公开随机连接密钥；默认必须由大屏允许请求。“自动允许下一台电脑”是接收端明确开启且用后即关的现场模式。
- WebRTC 媒体加密不能代替信令身份校验。
- Electron 界面仅加载本地资源，使用进程隔离、受限 preload 接口和权限处理器。

## 5. 开发顺序与每一步的交付物

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| M0：技术验证 | 本地采集预览；两台真实电脑按地址连接；传输整屏 | 路由器断开互联网后，接收端仍能播放另一台电脑的桌面 |
| M1：首个可试用版 | 两个角色入口、配对、源选择、全屏、停止、基本错误提示、绿色打包 | 非开发人员按短说明完成连接；错误配对被拒绝；停止后立即释放采集资源 |
| M2：讲座现场版 | 自动发现、网络诊断、掉线恢复、分辨率档位、本地日志、演示期间防休眠 | 完成真实讲座网络和设备上的一小时连续测试、重复连接及网络中断测试 |
| M3：扩展版 | 根据实际反馈评估 Mac、浏览器接收和更多电视系统 | 各平台分别验证权限、声音、网络和分发流程 |

M0 的内部验证程序不能直接作为现场正式版本分发。配对和身份验证在 M1 对外试用前完成。

## 6. 首版验收建议

以下是待验证的目标，不是已有性能数据：

- 以 1080p、最高 30fps 作为初始画质目标，提供 720p 回退；实际帧率随画面和网络变化。
- PPT 正文、中文小字和鼠标可辨认；屏幕比例保持正确。
- 播放动态课件或视频画面，记录画面连续性和延迟；声音同步不在本版验收范围。
- 从点击开始到接收端出现画面的目标为 5 秒以内，另行记录发现和配对耗时。
- 在指定测试设备、5GHz 局域网下，把端到端延迟 300ms 内作为初期优化目标。
- 连续使用至少 60 分钟，检查崩溃、黑屏、画面中断、CPU、内存和电池负载。
- 断开互联网测试；所有字体、脚本、图标、发现、配对和连接均不应依赖外部请求。
- 测试拒绝连接、错误码、过期码、重复会话、接收端已占用、主动停止、休眠恢复。
- 两台真实设备实测优先；同机双窗口只验证部分程序逻辑。
- getStats 的往返时延不等于端到端画面延迟；画面延迟通过同时拍摄发送屏和接收屏等方法测量。

## 7. 建议代码结构

```text
src/
  main/          桌面程序生命周期、采集、配对信令、发现
  preload/       界面与主进程之间的受限接口
  renderer/      首页、发送页面、接收页面
  shared/        消息格式、状态和输入校验
tests/           配对状态、会话清理、消息校验等自动化检查
docs/            双机测试步骤、网络诊断和发布说明
```

独立维护自己的源码，锁定依赖版本并保留必要的许可证说明。发布包无需联网授权或强制更新；后续兼容修复通过普通版本发布交付。
